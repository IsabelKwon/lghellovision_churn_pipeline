# LG헬로비전 해지 데이터 정제 파이프라인

2,289만 행(11개월, 217만 고객)의 해지 데이터를 **원본 CSV에서 정제된 분석용 데이터까지 명령 한 번으로** 만들고, **품질검사를 통과한 결과만 배포하는** 배치 파이프라인입니다.

```bash
python run_pipeline.py
```

## 한눈에 보기

| | 내용 |
|---|---|
| **파이프라인** | 원본 CSV → 정제 → 품질검사 → 배포 → 마트까지 6단계를 명령 한 번으로 실행. 같은 원본이면 몇 번을 돌려도 같은 결과 | 
| **데이터 품질 관리** | 정제 11종(경고 1종 포함) + 마트 4종 품질검사. 원본 = 정제 + 사유별 제외를 매번 대사하고, 배포를 막는 검사가 하나라도 실패하면 배포를 멈추고 기존 정상 데이터를 유지 |
| **데이터 모델링** | 원본(raw) / 정제(clean) / 마트(mart) 3계층 분리. 정제는 사실을 보존하고, 목적별 규칙(첫 해지 달까지만, 고객 단위 요약 등)은 마트에 둠 |
| **대용량 처리** | RAM 16GB 노트북에서 2,289만 행을 약 4분에 처리. 파일 단위 처리로 메모리 부족 문제를 해결하고, 실행 시간을 단계별로 재서 병목을 찾아 줄임 |
| **테스트** | pytest 7개로 정상 실행, 불량 데이터 차단, 배포 중단 시 기존 데이터 유지, 과거 버그 재발 방지를 확인 |
| **기술** | Python, SQL (DuckDB), Parquet, pytest |

**결과**: 22,893,471행 → 정제 22,053,564행 (제외 3.67%, 사유별로 전부 기록) → 모델링용 마트 21,314,472행 + 고객 단위 마트 2,135,261행. 검증 과정에서 해지 라벨(`cancel_yn`)이 달마다 바뀌는 상태가 아니라 고객마다 고정된 값이라는 것을 발견해, 기존 "월 해지율 0.71%" 해석을 바로잡고 세그먼트 해지율을 고객 기준으로 계산하도록 파이프라인을 고침. 확실한 지표는 관측 기간 중 해지 라벨 고객 비율 7.05% ([해지 라벨 검증](#해지-라벨-검증) 참고).

## 왜 만들었나

처음에는 Jupyter 노트북으로 정제했습니다. 정제 후 재검증에서 새 문제가 나올 때마다 이미 저장된 Parquet를 덮어쓰며 패치했고, 결과적으로 최종 파일은 **1차 정제 → `SCRB_PATH_NM_GRP` 패치 → `INHOME_RATE` 패치 → 숫자형 캐스팅** 네 단계를 거쳐 만들어졌습니다.

이 방식에는 세 가지 문제가 있었습니다.

- **재현 불가**: 셀 실행 순서에 따라 결과가 달라지고, 최종 파일에 어떤 수정이 반영됐는지 코드만 봐서는 알 수 없었습니다. 실제로 `INHOME_RATE` 수정은 코드는 있는데 파일에 반영되지 않은 상태로 한동안 남아 있었습니다.
- **검증이 수동**: 정제가 잘 됐는지 매번 눈으로 확인해야 했습니다.
- **새 데이터에 취약**: 다음 달 데이터가 들어오면 같은 작업을 사람이 다시 해야 했습니다.

그래서 노트북에 흩어진 정제 규칙을 SQL 파일 하나로 모으고, 눈으로 하던 확인을 자동 품질검사로 바꿨습니다.

## 스키마 검사

데이터 설명용으로 받은 샘플 파일은 실제 CSV와 버전이 달라, 같은 의미의 컬럼도 이름이 다르거나(`CH_FAV_RANK1` / `CH_FAV_RNK1`) 한쪽에만 있는 컬럼이 있었습니다. 이처럼 문서와 실제 파일은 언제든 어긋날 수 있습니다.

컬럼이 빠지거나 이름이 바뀐 파일이 들어오면 SQL이 중간에 에러를 내거나 조용히 틀린 결과를 냅니다. 그래서 2,289만 행 정제를 시작하기 전에 **파일 헤더만 읽어** 필수 컬럼을 확인하고, 다르면 바로 중단합니다. 비슷한 이름의 컬럼이 있으면 함께 알려줍니다.

같은 단계에서 `config.SEGMENT_COLS`(세그먼트 해지율을 볼 컬럼)에 없는 컬럼 이름이 있는지도 확인합니다. 이 검사가 없으면 오타 하나 때문에 정제를 약 3분 동안 다 돌린 뒤 마트 단계에서야 멈추고, 정제 데이터만 새로 배포된 상태가 됩니다.

```bash
python scripts/make_sample_data.py --spec-names   # 샘플 파일의 컬럼 이름으로 된 파일
python run_pipeline.py
# FAIL ...: 필수 컬럼 없음 → CH_FAV_RNK1 (혹시 CH_FAV_RANK1?), PAID_CHNL_CNT_GRP (혹시 PAID_CHNL_SCRB_CNT_GRP?)
# 스키마 불일치 → 정제를 시작하지 않고 중단합니다.
```

## 정제 규칙

행을 빼는 규칙(R1~R3c)은 `sql/02_drop_rules.sql`, 값을 바꾸는 규칙(R4~R9)은 `sql/03_clean.sql`에 있고, 코드 주석의 `[R1]`~`[R9]` 번호와 대응합니다.

| # | 대상 | 처리 | 근거 |
|---|---|---|---|
| R1 | `STB_RES_1M_YN='""'` 행 33건 | 제외 | 9개 컬럼에 동시에 센티널이 있음. 내부 테스트 또는 특수 계정으로 판단 |
| R2 | `AGE_GRP10='10대미만'` 6건 | 제외 | 한 분기에만 등장하고 표본이 너무 작음 |
| R3a | 라벨 충돌 고객 40,063명 전체 | 제외 | 같은 고객·같은 달에 `cancel_yn`만 다른 행이 공존하고, 이후 달에도 계속 충돌함. 어느 라벨이 맞는지 판단할 근거가 없음 |
| R3b | 39개 컬럼이 전부 같은 완전 중복 행 (현재 0건) | 한 행만 남기고 제외 | 같은 데이터가 두 번 들어간 것이라 한 행만 남기면 정보 손실이 없음 |
| R3c | 라벨은 같고 다른 컬럼이 다른 고객 전체 (현재 0건) | 제외 | 어느 값이 맞는지 판단할 근거가 없음. R3a와 사유를 나눠 새 유형의 중복이 들어오면 바로 보이게 함 |
| R4 | `AGMT_KIND_NM`, `AGMT_END_YMD`의 `정보없음` | NULL | 결측 값. `무약정`은 유효한 카테고리라 유지 |
| R5 | `SCRB_PATH_NM_GRP`의 `정보없음` (39,254건) | NULL | 정제 후 재검증 단계에서 새로 발견 |
| R6 | `INHOME_RATE`의 `알수없음` (3,030,808건) | NULL + DOUBLE 변환 | 0~100 척도 컬럼. 신규 고객 가설은 기각됐고 단순 결측으로 판단 |
| R7 | `CH_25_RATIO_MONTH1` > 100 (10건) | 100으로 캡핑 | 비율상 불가능한 값. 신규 고객의 3개월 평균 계산 edge case |
| R8 | 숫자형 10개 컬럼 | VARCHAR → DOUBLE | 트리 모델 학습에 필요 |
| R9 | `AGMT_END_YMD` (날짜와 `무약정`이 한 컬럼에 섞임) | `AGMT_END_DATE`(날짜) + `IS_NO_AGMT`(무약정 여부)로 분리, 원본 컬럼은 유지 | 문자로 비교하면 `'무약정' > '20240101'`이 참이 되어 조건 검색이 조용히 틀림. 날짜 계산(만료까지 남은 일수)도 불가능 |

**그대로 유지한 값**: `기타`(주요 항목 외 나머지를 묶은 정상 카테고리), `연령없음`(사업자 계정 세그먼트로 통계 검증함), `3개월내없음`, `무약정`. **결측(`정보없음`, `알수없음`)과 정상 카테고리(`기타`)를 구분하는 것**을 정제 원칙으로 삼았습니다.

## 제외 내역 기록 (행 대사)

처음에는 "전체 제외율 10% 이하"만 확인했습니다. 이 방식으로는 R1이 갑자기 수만 행을 걸러내도 전체 비율이 10% 아래면 알 수 없습니다. 그래서 행을 빼는 방식을 바꿨습니다.

1. `02_drop_rules.sql`이 모든 행에 제외 사유(`_drop_reason`)를 붙입니다.
2. 파이프라인이 사유별 개수를 셉니다.
3. `03_clean.sql`은 사유가 없는 행만 가져갑니다.
4. 품질검사가 **원본 = 정제 + 사유별 제외의 합**이 정확히 맞는지, 규칙마다 비율이 상한(`config.RULE_MAX_DROP_RATE`) 안인지 확인합니다.

제외 규칙이 한 파일에만 있고, 정제와 개수 집계가 같은 정의를 쓰기 때문에 둘이 어긋날 수 없습니다.

```
[2/6] sha_tps_cancel_202302_to_202304.csv: 원본 N행 → 제외 R1_corrupted_row a, R3a_label_conflict b
[3/6] PASS drop_reconciliation  원본 N = 정제 M + 제외 K (일치, 제외율 x%) | R1_corrupted_row …, R2_age_under_10 …, R3a_label_conflict …
```

이 과정에서 기존 필터의 버그도 고쳤습니다. 이전에는 `WHERE STB_RES_1M_YN != '""'`로 걸렀는데, SQL에서 `NULL != '""'`의 결과는 참이 아니라 NULL이라서 **값이 비어 있는 정상 행까지 조용히 빠졌습니다.** 실제 데이터에는 NULL이 없어서 결과가 같았지만, 새 데이터에 빈 값이 들어오면 사라졌을 겁니다. `CASE` 문은 NULL이면 다음 조건으로 넘어가므로 지정한 값만 정확히 제외합니다. 샘플 데이터에 빈 값 행 2개를 넣어 두었고, 새 방식에서는 제외되지 않고 남습니다.

## 품질검사

| 검사 | 확인 내용 | 잡아내는 문제 |
|---|---|---|
| `drop_reconciliation` | 원본 = 정제 + 사유별 제외, 규칙별 비율 상한, 전체 제외율 10% 이하 | 규칙에 없는 이유로 행이 사라짐, 특정 규칙이 평소와 다르게 동작 |
| `primary_key_unique` | `sha2_hash + p_mt`가 비어 있지 않고 유일 | 고객×월 스냅샷 구조가 깨짐 |
| `agmt_date_split` | 날짜여야 하는 `AGMT_END_YMD` 값이 전부 `AGMT_END_DATE`로 변환됨 | 날짜 형식이 바뀐 데이터 유입 (`TRY_STRPTIME`도 실패 시 조용히 NULL) |
| `no_conflicted_customers` | 고객 전체 제외 대상(R3a·R3c) 0명 | R3a·R3c 누락 |
| `no_forbidden_sentinels` | `정보없음`·`알수없음`·`""`·`10대미만` 0건 | 정제 규칙 누락, 새 센티널 유입 |
| `numeric_types` | 숫자형 12개 컬럼이 DOUBLE | 캐스팅 누락 |
| `no_unexpected_nulls` | `INHOME_RATE` 외 숫자형 NULL 0건 | **`TRY_CAST`가 변환 실패를 조용히 NULL로 바꾸는 문제** |
| `ratio_range_0_100` | 비율 컬럼 0~100 | 캡핑 누락 |
| `target_values` | `cancel_yn` ∈ {유지, 해지}, NULL 없음 | 타겟 오염 |
| `label_fixed_per_customer` (경고) | 달이 바뀌며 `cancel_yn`이 바뀐 고객 0명 | 라벨 정의 변경 (고객별 고정 → 월별 상태) |
| `month_format` | `p_mt`가 YYYYMM 형식 | 날짜 형식 변경 |

`label_fixed_per_customer`는 **배포를 막지 않고 경고만 하는 검사**입니다. 실제 데이터에서는 달이 바뀌며 라벨이 바뀐 고객이 0명(유지 → 해지 0명, 해지 → 유지 0명)이고, 마트의 해석(첫 해지 행 = 첫 관측 달, 확실한 지표 = 해지 고객 비율)이 이 사실에 기대고 있어서 이 가정이 깨지면 알 수 있게 했습니다. 처음에는 "해지 후 유지로 돌아간 고객이 있으면 실패"로 만들었지만, 재가입이나 해지 철회는 현실에서 정상적인 일이라 데이터 오류로 보고 배포를 막는 것은 맞지 않다고 판단해 바꿨습니다. 로그에는 `WARN`으로 표시됩니다.

실패 시연:

```bash
python scripts/make_sample_data.py --inject-bad   # 숫자 컬럼에 'N/A' 섞인 데이터
python run_pipeline.py
# FAIL no_unexpected_nulls  예상 밖 NULL: {'TOTAL_USED_DAYS': 4}
# 품질검사 실패 → 배포 중단. 기존 churn_clean 는 그대로 유지됩니다.
```

`TRY_CAST`는 에러 없이 NULL을 만들기 때문에 이 검사가 없으면 결측이 조용히 늘어납니다.

## 마트

정제 데이터는 원본을 깨끗하게 만든 것이고, 마트는 **특정 목적에 맞게 가공한 것**입니다. 둘을 나눈 이유는 아래 `churn_base`의 규칙 때문입니다.

**`churn_base` — 모델링용 월별 테이블**

해지 고객 1명은 여러 달에 걸쳐 `해지` 행으로 나타납니다 (해지 고객 150,613명, 1명당 `해지` 행 평균 5.9개). 행을 그대로 세면 같은 고객을 여러 번 세게 되므로(행 비율 4.034%), 고객마다 **첫 `해지` 행까지만** 남기고 `is_churn`(0/1) 컬럼을 추가해 고객당 해지 행이 1개가 되도록 했습니다.

> **주의**: 처음에는 "첫 `해지` 행 = 해지가 일어난 달"로 보고, 이 기준으로 계산한 0.707%를 "실제 월 해지율"이라고 설명했습니다. 이후 검증에서 **이 해석이 틀렸다**는 것을 확인했습니다. 해지 고객의 96.1%는 데이터 첫 달(2023-02)부터 이미 `해지`이고, `유지`에서 `해지`로 바뀐 고객은 한 명도 없습니다. 그래서 "첫 `해지` 행"은 대부분 해지한 달이 아니라 데이터가 시작된 달이며, 0.707%는 월 해지율이 아닙니다. 자세한 근거는 아래 [해지 라벨 검증](#해지-라벨-검증)에 있습니다. 마트의 규칙 자체(고객당 해지 행 1개)는 그대로 두었고, 해지 시점을 어떻게 정할지는 `cancel_yn`의 정의를 데이터 제공처에 확인한 뒤 정할 과제로 남겼습니다.

**결정**: 해지 고객은 **처음 나온 달의 행 1개**를 기준 행으로 씁니다. 이 행은 "해지한 달"이 아니라 "그 고객이 처음 관측된 달"이며, 해지를 고객당 한 번만 세기 위한 기준입니다. 실제 데이터에서 해지 고객 150,613명 모두 `churn_base`에 1행씩 남아 있고, 그중 144,728명(96.1%)의 행이 2023-02입니다. 유지 고객은 나온 달을 모두 남기므로, `churn_base`의 해지 행 비율(0.707%)은 월 해지율이 아닙니다. 그래서 해지 비율은 아래 `customer_churn`(고객 1명 = 1행)으로 계산합니다.

이 규칙은 정제 단계에 넣지 않았습니다. 정제 데이터는 원본의 사실을 보존하고, 목적에 따라 행을 자르는 규칙은 마트에 둔다는 원칙 때문입니다.

**`customer_churn.parquet` — 고객 1명 = 1행**

| sha2_hash | is_churner | first_observed_mt | last_observed_mt | n_months | 세그먼트 컬럼 5개 |
|---|---|---|---|---|---|
| 고객 식별값 | 해지 라벨 고객이면 1 | 처음 나온 달 | 마지막으로 나온 달 | 나온 달 수 | 처음 나온 달의 값 |

- `cancel_yn`은 고객마다 고정된 라벨이므로, 해지 비율은 행이 아니라 **고객 수로** 셉니다. 실제 데이터에서 2,135,261행, 해지 고객 150,613명(**7.05%**)입니다.
- `last_observed_mt`는 사실(마지막으로 관측된 달)만 기록합니다. 실제 해지 시점은 추정이라 "해지한 달" 컬럼은 만들지 않았습니다.
- 세그먼트 값은 **처음 나온 달의 값**을 씁니다. 마지막 달 값을 쓰면 해지 직전의 해지 문의 급증 같은 "해지의 결과"가 섞이기 때문입니다.

**`segment_churn.parquet` — 세그먼트별 해지 고객 비율**

| segment_col | segment_value | customers | churners | churn_rate_pct | lift |
|---|---|---|---|---|---|
| AGMT_END_SEG | 약정만료전 1개월 | 14,096 | 3,474 | 24.645 | 3.494 |

- `churn_rate_pct` = 그룹의 해지 고객 수 / 그룹의 고객 수 (`customer_churn` 기준).
- `lift` = 그룹의 `churn_rate_pct` / 전체 해지 고객 비율(7.05%). 1보다 크면 평균보다 해지 고객 비율이 높은 그룹입니다.
- 세그먼트 컬럼은 `config.SEGMENT_COLS`에서 관리합니다. 컬럼을 추가해도 테이블 구조는 그대로입니다(세로형).

**행 기준에서 고객 기준으로 바꾼 이유**: 처음에는 `churn_base`의 행으로 셌습니다(해지 행 수 / 전체 행 수). 그런데 해지 고객은 1행, 유지 고객은 관측된 달 수만큼 행이 있어서, 유지 고객이 오래 관측된 그룹일수록 해지 비율이 낮아 보입니다. 예를 들어 유지 고객 A(11개월)와 해지 고객 B가 있는 그룹은 행 기준 1/12 = 8.3%, 고객 기준 1/2 = 50%입니다. 실제 데이터에서 두 기준을 비교해 보니 순위가 바뀌는 세그먼트가 있었습니다.

| 세그먼트 | 행 기준 (이전) | 고객 기준 (현재) |
|---|---|---|
| 약정만료전 6~9개월 | 10위 (1.08%) | **5위** (14.29%) |
| 약정만료후 1개월~2개월 | 11위 (0.96%) | **6위** (13.01%) |
| 약정만료후 3~6개월 | 6위 (1.16%) | **9위** (11.15%) |
| 가입 6개월미만 / 6~12개월미만 | 2위 / 3위 | **3위 / 2위** |

**마트 품질검사**

| 검사 | 확인 내용 |
|---|---|
| `mart_one_churn_per_customer` | 고객마다 해지 행이 최대 1개이고, 그 행이 마지막 행인지 |
| `mart_no_customer_lost` | 행은 줄어도 고객 수는 정제 데이터와 같은지 |
| `mart_customer_one_row` | `customer_churn`이 고객 1명 = 1행이고, 고객 수·해지 고객 수가 정제 데이터에서 직접 센 값과 같은지 |
| `mart_segment_totals` | 세그먼트별 고객 수 합계가 `customer_churn` 전체 고객 수와 같은지 |

## 해지 라벨 검증

"첫 해지 달까지만 남기면 실제 월 해지율이 나온다"는 설명의 근거를 코드로 확인하다가, 그 전제가 틀렸다는 것을 발견했습니다.

### 1. 기존 가정

데이터는 고객 × 월 스냅샷이므로, 고객이 `유지`로 지내다가 어느 달에 `해지`로 바뀐다고 가정했습니다. 그래서 마트(`churn_base`)는 고객별 첫 `해지` 행을 해지 시점으로 보고, 이를 기준으로 계산한 0.707%를 월 해지율로 설명했습니다.

### 2. 가정과 다른 점

이 설명을 보여줄 예시로 "해지 전 `유지` 달과 해지 후 `해지` 달이 모두 있는 고객"을 찾았으나, 정제 데이터의 고객 2,135,261명 중 **`유지` 행과 `해지` 행을 모두 가진 고객이 한 명도 없었습니다.**

### 3. 가설

- **가설 A**: `cancel_yn`은 월별로 바뀌지 않고 고객마다 고정된 값이다.
- **가설 B (대안)**: `유지` → `해지`로 바뀐 고객이 충돌 고객(R3a)으로 분류되어 정제 단계에서 빠졌다.

### 4. 검증

원본 CSV와 정제 데이터로 확인했습니다.

| # | 확인한 것 | 결과 | 의미 |
|---|---|---|---|

| 2 | 충돌 고객 40,063명의 월별 모양 | 처음 나온 달부터 **매달** 두 줄. 바뀌는 순간이 없음 | 가설 B 기각 |

### 5. 결론

- **확인된 것**: `cancel_yn`은 월별 사건이 아니라 고객마다 고정된 값입니다. 따라서 "첫 `해지` 행"은 해지한 달이 아니고, 이를 기준으로 계산한 0.707%는 월 해지율이 아닙니다. 확실하게 말할 수 있는 지표는 **관측 기간 중 해지 라벨이 붙은 고객 비율 7.05%**(150,613 / 2,135,261)입니다.
- **추정 (확인 필요)**: 해지 고객이 달마다 데이터에서 사라지고 사라지기 직전으로 갈수록 이용이 줄어드는 것으로 보아, `cancel_yn`은 "관측 기간 중 해지한 고객"이라는 꼬리표를 모든 달에 붙인 것이고 실제 해지는 데이터에서 사라지는 무렵에 일어났을 가능성이 높습니다. 데이터 제공처의 정의를 확인하기 전까지는 추정으로 둡니다.
  - 근거 (`investigate_churn_rows.py` [6]): 해지 고객은 90.5%(136,244 / 150,613명)가 2023-12 전에 사라지지만 유지 고객은 0.20%(4,056 / 1,984,648명)만 사라집니다. 사라진 해지 고객의 해지·정지 문의 비율은 사라지기 직전 달에만 **26.0%** 로, 같은 고객의 이전 달들(3.5%)보다 약 7.5배 높고, 1~6개월 전은 2.8~5.1%입니다. "해지 후 N개월 뒤 삭제"라면 해지 문의가 N개월 전에 몰려 있어야 하는데 그런 모습이 없어, 해지한 달을 끝으로 기록이 끊긴다고 보는 것이 가장 자연스럽습니다.

### 6. 조치

- README와 코드 주석에서 잘못된 해석("월 해지율 0.707%")을 바로잡고, 확인된 사실과 추정을 나눠 기록했습니다.
- 누구나 재현할 수 있도록 검증 스크립트 2개를 추가했습니다.
- 샘플 데이터와 다른 점을 확인해 기록했습니다. `scripts/make_sample_data.py`는 기존 가정("유지로 지내다가 어느 달에 해지로 바뀐다")대로 샘플을 만들기 때문에, 샘플로 위 스크립트를 돌리면 "달이 바뀌며 라벨이 바뀐 고객"이 나옵니다(고객 3,000명 샘플에서 790명). 이 검증 결과는 실제 데이터에서만 재현됩니다.
- **파이프라인 수정**: 고객 단위 마트 `customer_churn`(고객 1명 = 1행)을 추가하고, `segment_churn`을 해지 행 비율에서 **해지 고객 비율**로 바꿨습니다. 행 기준으로 세면 유지 고객이 오래 관측된 그룹일수록 해지 비율이 낮아 보여, 실제 데이터에서 약정 구간 세그먼트의 순위가 바뀌는 것을 확인했기 때문입니다([마트](#마트) 참고). 확실한 지표 7.05%도 이제 스크립트가 아니라 파이프라인 결과물에서 나옵니다.
- **품질검사 추가**: 달이 바뀌며 라벨이 바뀐 고객이 생기면 경고하는 `label_fixed_per_customer`를 넣었습니다. 위 해석이 모두 "라벨은 고객별 고정"이라는 사실에 기대고 있어서, 원천 데이터의 정의가 바뀌면 알 수 있게 하기 위해서입니다.
- `churn_base`의 규칙(해지 고객은 첫 행 1개)은 모델링용으로 그대로 두었습니다. 실제 해지 시점은 추정이라 마트에 넣지 않고, 마지막으로 관측된 달(`last_observed_mt`)이라는 사실만 제공합니다. `cancel_yn`의 정의는 데이터 제공처에 확인할 과제로 남겼습니다.

### 7. 배운 점

데이터 구조는 가정하지 않고 확인해야 합니다. 새 데이터를 받으면 라벨이 시간에 따라 어떻게 바뀌는지부터 확인합니다.

## 설계에서 고민한 점

**대용량 처리 (RAM 16GB 노트북)**
- 처음에는 `duckdb.sql(...).df()`로 2,289만 행을 pandas에 올리다가 OOM이 났습니다. 그래서 pandas를 거치지 않고 DuckDB `COPY ... TO PARQUET`로 디스크에 바로 쓰도록 바꿨습니다.
- 파일을 하나씩 처리해 최대 메모리와 임시 디스크 사용량을 약 1/4로 줄였습니다. DuckDB 메모리 4GB, 스레드 2개, 임시 디렉토리 2GiB로 제한했습니다.
- 충돌 고객은 분기 파일을 넘나들 수 있어서 이 단계만 전체 파일을 대상으로 합니다. 먼저 2개 컬럼만 읽어 중복 키를 찾고, 그 키에 해당하는 행의 해시는 파일 1개씩 만들어 모은 뒤 한 번에 비교해 케이스를 나눕니다. (전체 컬럼을 4개 파일에서 한꺼번에 읽으면 임시 디스크 2GiB를 넘어 실패했습니다)
- 완전 중복(R3b)을 처리하려고 `row_number()`로 줄 번호를 매기는 규칙을 추가했더니, 전체 실행이 227초에서 342초로 느려졌습니다. 단계별 시간을 비교해 정제 단계가 94초에서 179초로 두 배가 된 것을 찾았고, 같은 파일로 `row_number()`가 있을 때와 없을 때를 재서 원인을 확인했습니다. 실제 데이터에는 완전 중복이 0건이라, 완전 중복이 있을 때만 `row_number()`를 계산하도록 바꿨습니다. 정제 단계는 85초로 돌아왔고, 결과는 행 수와 체크섬으로 기존과 같음을 확인했습니다.

**재현성과 안전한 배포**
- 모든 정제 규칙이 SELECT 하나에 있어서 "원본 + 코드 = 항상 같은 결과"가 됩니다. 몇 번을 다시 돌려도 결과는 같습니다.
- 결과를 임시 폴더에 먼저 쓰고, 검사를 통과했을 때만 최종 폴더와 교체합니다. 검사에 실패해도 분석가가 쓰던 데이터는 깨지지 않습니다.
- `SELECT * REPLACE(...)`로 원본 컬럼 순서를 유지합니다. 노트북 방식에서는 수정한 컬럼이 맨 뒤로 밀렸습니다.

**월 단위 파티셔닝**
- 데이터가 고객×월 스냅샷 구조라서 `p_mt=YYYYMM/` 폴더로 나눠 저장합니다. 특정 월만 읽을 수 있고, 매달 새 데이터를 추가하는 구조로 확장하기 쉽습니다.

**인프라 트러블슈팅**
- OOM을 해결한 뒤에는 디스크 부족 에러가 났습니다. 파일 분할과 DuckDB 설정만으로는 해결되지 않아 원인을 추적한 결과, 사용하지 않는 Docker Desktop의 WSL 가상 디스크(`docker_data.vhdx`)가 19GB를 차지하고 있었습니다. 이를 정리해 여유 공간을 6.8GB에서 51.75GB로 늘렸습니다.

마지막 테스트는 실제로 겪은 버그를 막기 위한 것입니다. 처음에는 비율 상한을 `LEAST(값, 100)`으로 처리했는데, DuckDB의 `LEAST`는 NULL을 무시해서 `LEAST(NULL, 100) = 100`이 됩니다. 빈 값이나 숫자가 아닌 값이 조용히 "100%"로 바뀌고 NULL 검사도 통과하는 문제였습니다. 실제 데이터에는 해당하는 값이 없어 결과는 같았지만, `CASE` 문으로 바꾸고 테스트를 추가했습니다. `LEAST`로 되돌리면 이 테스트가 실패하는 것을 확인했습니다.

## 한계와 다음 과제

- **고정된 품질 기준**: 규칙별 제외 비율 상한(`config.RULE_MAX_DROP_RATE`)은 실제 실행 결과에 여유를 둔 고정값입니다(예: R3a 실제 3.67% → 상한 5%). 데이터가 정상적으로 바뀌어도 상한을 넘으면 배포가 멈추고, 반대로 상한 안에서 비율이 크게 변하면 알아채지 못합니다. 지금은 상한에 걸리면 사람이 원인을 확인하고, 원천 오류면 원천 담당자에게 알리고, 정상적인 변화면 config의 상한을 조정합니다. 실행마다 품질 리포트(JSON)를 `logs/`에 남기고 있으므로, 다음 단계로 **지난 실행 대비 변화량**(예: R3a 비율이 1%p 이상 변하면 실패)으로 검사하고, 조금 벗어나면 경고만 하는 두 단계 기준을 두는 방식을 생각하고 있습니다.
- **허용 값 목록 검사**: 지금은 금지 값 목록(`정보없음` 등) 방식이라, 처음 보는 값(예: `미확인`)이 들어오면 통과합니다. 범주형 컬럼마다 허용 값 목록을 두는 방식이 더 튼튼합니다.
- **월별 데이터 양 검사**: 어떤 달의 행 수가 전월 대비 급감해도 지금은 알 수 없습니다.
- **컬럼 간 논리 검사**: `AGMT_END_SEG`(약정 종료 구간)와 `AGMT_END_DATE`가 서로 맞는지 등. 규칙이 실제 데이터에서 성립하는지 먼저 확인이 필요합니다.
- **충돌 고객 제외의 편향**: 충돌 고객은 사업장 계정 비율이 약 2배라, 통째로 빼면 사업장 고객이 덜 반영될 수 있습니다 (전체의 1.84%).
- **해지 시점 정의**: `churn_base`는 고객별 첫 `해지` 행을 해지 행으로 쓰지만, 이 행은 대부분 데이터 첫 달(2023-02)의 행이라 해지 시점이 아닙니다([해지 라벨 검증](#해지-라벨-검증)). 해지를 **예측**하는 모델을 만들려면 먼저 `cancel_yn`의 정의를 데이터 제공처에 확인하고, 정의에 따라 해지 시점(예: 데이터에서 마지막으로 나온 달)을 다시 정한 뒤, 그 전 달의 정보로 해지를 맞히도록 시점을 맞춰야 합니다.
